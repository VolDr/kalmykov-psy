# Развёртывание исправлений безопасности

Изменения подготовлены для SvelteKit 3.1, adapter-node 6, Vite 8 и Node 26.12.1 (версия записана в `.nvmrc`). На production эти изменения из локальной рабочей копии ещё не развёрнуты.

## Перед переключением приложения

1. Сохранить резервную копию БД и убедиться, что установлен Node нужной версии именно для процесса приложения, а не только для интерактивного shell.
2. Установить зависимости из нового lockfile командой `npm ci` в среде сборки.
3. Применить `drizzle/0022_security_rate_limits.sql` к той же PostgreSQL, которую использует приложение. В штатной среде с журналом Drizzle она включена в `npm run db:migrate`. Если прежние SQL применялись вручную, не запускать заново все старые миграции: применить именно 0022 обычным способом администрирования БД.
4. Выполнить `npm test` и `npm run build`. Тесты используют собственную PostgreSQL в памяти; production-БД им не нужна.
5. Перезапустить приложение через его фактический менеджер процессов и проверить его executable/runtime. Замена `nvm use` без перезапуска не обновляет действующий процесс.

Таблица `security_rate_limits` обязательна. Если она отсутствует или БД недоступна, защищённые публичные действия и вход возвращают 503, а не пропускают запрос без лимита. Поэтому миграция должна быть применена **до** запуска новой версии. Она добавляет таблицу и индекс, не изменяя данные клиентов.

## Origin и адрес клиента

Публичный origin задан в `vite.config.ts`: `https://kalmykov-psy.ru`. Если эта же сборка используется на другом домене, изменить `paths.origin` перед сборкой. Старый `ORIGIN` больше не управляет adapter-node 6.

Лимиты используют `event.getClientAddress()`. Если сайт работает через nginx, настроить `ADDRESS_HEADER` / `XFF_DEPTH` в окружении процесса под фактическую цепочку доверенных прокси. nginx должен перезаписывать соответствующий заголовок, а прямой доступ к порту Node следует ограничить. Без настройки адреса все пользователи за одним reverse proxy могут делить один IP-лимит; принимать адрес от произвольного внешнего клиента тоже нельзя.

## Что проверить после запуска

- Гость получает отказ на `/admin`, на POST-действиях и на запросах `/admin/.../__data.json?x-sveltekit-invalidated=001`. Администратор может войти и работать с данными.
- Открытая форма обратной связи принимает одну отправку. Повторная, закрытая или скрытая форма отклоняет изменение; старые ссылки продолжают открываться. Новые ссылки используют 128-битные случайные токены.
- Бронирование и оплата работают; секреты/подписи Telegram и Robokassa проверяются их обработчиками. Общая защита не читает и не меняет исходные тела вебхуков.
- При превышении лимита возвращается 429 и Retry-After. Лимит email действует по получателю, даже если меняется IP; login имеет независимые лимиты по IP и имени аккаунта.
- В новых логах нет хешей паролей, токенов подтверждения и объектов подписчиков. Старые логи этим изменением не очищаются.

## Остаётся открытым

SEC-02 (секреты в Git/архивах и их ротация), SEC-08 (проверка подписи Instagram при отсутствии секрета), SEC-09 (подпись персональных ссылок/привязки контакта) не исправлялись по поручению пользователя. Их актуальный статус указан в отчёте аудита. Также отдельно остаётся настройка SSH/firewall и обновлений ОС.
